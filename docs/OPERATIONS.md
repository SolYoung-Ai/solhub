# SolHub · 安全与稳定性审计 + 增长后的升级维护方案

> 审计时间：2026-11-01　　对应线上版本：Worker `93d50217`、前端 `main`
> 结论摘要：**当前架构能安全支撑到日活约 500–1000**，但有两个必须提前知道的硬约束：
> ① Cloudflare 免费版 **KV 每天只有 1,000 次写入**；② 一次世界页加载会放大成 **约 180 次 KV 读**。
> 也就是说——**真正的瓶颈是"读放大"和"写配额"，不是用户数**。不解决这两个，加钱也撑不住。
>

## 〇、架构变更记录 · 2026-11-02 迁到 CloudBase（上海）

### 为什么迁

线上用户反馈「个人主页加载很慢而且登录不上」。分项计时把根因定位得很清楚：
DNS 0.003s、TCP 0.25s、TLS 0.58s 都正常，**卡在 TTFB 3.8~13.2 秒**，偶尔 TCP SYN 直接丢包；
`cf-ray` 显示 Cloudflare 免费版把国内用户调度到了 **LAX** 机房（免费版没有中国 PoP）。
代码层怎么优化都救不回来——一个零逻辑的根路由也要 1.5~6.7 秒。

于是把认证服务整体搬到**腾讯云 CloudBase（上海地域）**。实测接口响应 **0.13 秒**。

### 变更后的架构

| 层 | 技术 | 托管 | 说明 |
|---|---|---|---|
| 页面 | Astro SSG + React Islands | GitHub Pages | 不变 |
| 账号 / 创作者名录 / 关注 | CloudBase HTTP Function | `solyoung-d4gpp1f7s4e075f6d-1499756427.ap-shanghai.app.tcloudbase.com/api` | 原 Cloudflare Worker，机房从 LAX 变成上海 |
| 数据 | CloudBase PostgreSQL `public.kv` | 腾讯云 PG（上海） | 原 Cloudflare KV；**强一致**，彻底消除 30~60 秒最终一致窗口；写入不再有 1,000 次/天的配额 |
| 定时任务（每日数据备份） | CloudBase Event Function `solhub-cron` | 腾讯云 SCF | 原 Worker 的 cron 触发器（HTTP 函数不支持 timer 触发器）；官方推荐帖已随发帖功能下线 |
| 目录数据 | `src/data/*.json` 构建期产物 → PG | `catalog:community:v1` / `catalog:index:v1` | 灌入脚本换成 `scripts/seed-catalog-pg.mjs` |

### 代码怎么做到「一份逻辑，两处运行」

`worker/index.js` 仍是**业务逻辑唯一真源**。`scripts/sync-cloudbase-fn.mjs` 把它转成 CommonJS
（`export default {` → `module.exports = {`）生成 `core.cjs`，分别放进两个云函数目录。
云函数侧只有薄薄的适配层：

- `cloudbase/functions/solhub-auth/`（HTTP Function）：`index.js` 把 Node `http` 请求翻译成
  Workers 的 `fetch(request, env, ctx)`，再把 `Response` 翻译回去；监听 9000 端口。
- `cloudbase/functions/solhub-cron/`（Event Function）：`index.js` 只做定时触发 → `scheduled()`。
- `kv.cjs`：Workers KV 接口（get/put/delete/list）→ PostgreSQL 的 `public.kv` 表。
  `expirationTtl` 映射到 `expires_at` 列，读时过滤过期行。**KV 的最终一致性问题在这里消失**。
- `caches.cjs`：Workers Cache API（限流计数用）→ 进程内 Map。原来的 Cache API 边缘读写延迟
  极不稳定（曾出现 18 秒+ 卡死，直接导致接口间歇超时），换成进程内 Map 后延迟是微秒级，
  限流反而更准（同一实例内计数一致）。

### 新增的运维要点

- **头像外置（2026-11-04）**：头像是全站最「便宜又最贵」的字段 —— 单条用户记录里
  90% 是 base64 头像，而 `/creators`、`/search`、关注列表这些接口要枚举全部账号，
  等于每次请求都把所有人的图片字节读进内存再丢掉。现在：
  - `user:<email>` / `profile:<login>` 只留 `hasAvatar: true`（约 0.3~0.6KB）
  - `avatar:<sid>`（sid = 邮箱或 GitHub 登录名）存原始值（data URL 或外链）
  - 列表接口只回 `/avatar/<login>` 短链接；发字节的只有 `GET /avatar/<login>`
  - **改邮箱时必须搬 `avatar:<旧邮箱>` → `avatar:<新邮箱>`**（已实现，别漏）
  - 一次性迁移：`POST /admin/externalize-avatars`，默认 `dryRun`，传 `{"dryRun":false}` 才写库
- **`/creators` 有 60 秒实例内缓存**（`creatorsCache`）：命中时零 KV 读、零产品合并。
  写路径（改资料、认证、封禁、改名、注销）调用 `dropCreatorsCache()` 立刻失效；
  其它函数实例最多晚 60 秒。**新增会影响名录的写接口时记得调它。**
- **`/creators` 支持 `limit` / `offset` 分页**，返回 `hasMore` / `nextOffset`。
  默认一页 100，上限 200；一次最多枚举 `CREATORS_SCAN = 2000` 个账号。
- **CORS 归属**：CloudBase 网关的「跨域设置」若开启，会按环境安全域名白名单自动补
  `Access-Control-Allow-Origin`；本环境是**体验版套餐，加不了自定义安全域名**，
  所以路由上关掉跨域校验（`enableSafeDomain=false`），由函数自己发 CORS 头
  （`CORS_MODE=self`，白名单逻辑沿用 Worker 里原有的 `corsFor()`）。
  **注意**：如果函数和网关同时发 ACAO，响应头会变成 `<origin>,*`，浏览器直接拒绝 ——
  表现是「服务挂了」，不是「CORS 配错了」。
- **会话 Cookie 现在是跨站 Cookie**：Cookie 由接口域名（`app.tcloudbase.com`）设置，
  页面在 `solhub.solyoung.top`，两者不同站。Cookie 已带 `SameSite=None; Secure`，浏览器会带上；
  但如果浏览器/插件开了「拦截三方 Cookie」，登录态会丢失 —— 遇到这种反馈先查这里。
- **限流计数在进程内**：云函数实例被回收后计数会清零。限流本就是粗粒度防线，
  邮件发码的硬防线仍在阿里云控制台的「日发送量上限」。
- **PG 表 `public.kv`**：只有 `service_role`（云函数里的 API Key）能读写，
  `anon` / `authenticated` 无任何授权且 RLS 开启 → 浏览器直连一律被拒。
- **迁移脚本**：`scripts/migrate-kv-to-pg.mjs`（CF KV → PG，已跑过一次，36 个键）。
  切换前需要再跑一次以补齐期间的新数据。

### 待用户侧确认

- CloudBase 环境是**体验版**（`baas_trial`，2027-04-04 到期）。到期前需要升级套餐，
  否则服务会停。升级后可加自定义安全域名，把 CORS 交回网关统一处理。
- GitHub OAuth 的回调地址 `WORKER_URL + /callback` 已改成新域名，
  需要在 GitHub OAuth App 的回调白名单里同步更新，否则 GitHub 登录会失败。

## 一、架构现状

> ⚠️ 本节记录的是 **2026-11-02 迁移前** 的架构（Cloudflare Worker + Workers KV）。
> 当前架构见上文「〇、架构变更记录」。

| 层 | 技术 | 托管 | 额度影响 |
|---|---|---|---|
| 页面 | Astro SSG + React Islands | GitHub Pages | 不占 Worker 额度，CDN 全球分发，最稳 |
| 账号 / 帖子 / 评论 / 关注 | Cloudflare Worker | `solhub-auth.solyoung.top` | 占 Workers 请求 + CPU |
| 数据 | Workers KV（`PROFILES` 命名空间） | Cloudflare KV | **写入 1,000 次/天是全局最紧的约束** |
| 目录数据 | `src/data/*.json` 构建期产物 → KV 缓存 | `catalog:community:v1` / `catalog:index:v1` | 读取为主，量小 |

### Cloudflare 免费版额度（每日 00:00 UTC 重置）

| 项目 | 免费额度 | 付费版（$5/月起） |
|---|---|---|
| Workers 请求 | 100,000 次/天 | 1,000 万次/月 + $0.30/百万 |
| Workers CPU | **10 ms/请求**（超出即终止，报 1102） | 30 秒/请求（可调到 5 分钟） |
| 子请求 | 50/请求 | 10,000/请求 |
| KV 读 | 100,000 次/天 | 1,000 万次/月 + $0.50/百万 |
| **KV 写** | **1,000 次/天** | 100 万次/月 + $5/百万 |
| KV 删除 / 列举 | 各 1,000 次/天 | 同上 |
| KV 存储 | 1 GB | 1 GB + $0.50/GB/月 |
| KV 单键大小 | 25 MiB | 25 MiB |

### 一次操作消耗多少 KV 读写

| 操作 | KV 写 | KV 读 |
|---|---|---|
| 发一条帖子 | 5（帖子 + 点赞 + 评论 + 全局流 + 个人流） | ≈180（见下） |
| 发一条评论 | 1 | 1 + 帖子评论数组 |
| 注册账号 | 3（user + handle + session） | 1 |
| 改一次资料 | 1 | 1 |
| **发一封验证码** | **2**（码键 + meta 键） | 2 |
| **加载一次世界页** | 0 | **≈180** |

> **读放大从哪来**：`feedPosts()` 会取 feed 列表里前 60 条帖子，每条帖子再分别读 `post:<id>` / `post:<id>:likes` / `post:<id>:comments` 三个键 → 60 × 3 = **180 次读**。
> 推论：10 万次/天的读额度，只够约 **550 次世界页加载**。这就是为什么"用户不多也会卡"。

### 本次已经做的关键优化

把**大部分限流计数从 KV 挪到 Workers 内置 Cache API**：

- 发帖限流（30 秒一条）→ 每次发帖省 1 次 KV 写
- 评论限流（10 秒一条）→ 每次评论省 1 次 KV 写
- 登录失败计数 / 注册计数 / check-url 计数 → **0 次 KV 写**

带来的两个好处：
1. 正常流量下每帖从 6 次写降到 5 次写；
2. **攻击者无法通过暴力破解 / 刷号来烧光 KV 写配额**（否则等于花几分钟把整站发帖功能打死）。

> ⚠️ **但 Cache API 不是万能的**：它是 *data center local*（官方文档明说数据不跨机房同步）。
> 本项目实测连续请求的 `cf-ray` 会落在 `LHR` → `AMS` 之间跳变，跨机房时计数各算各的，**限流会静默失效**。
> 所以 Cache API 只适合当「粗粒度兜底」，凡是「失效会让用户直接失败」的逻辑都不能只靠它。

### 邮箱验证码为什么不用"固定键存当前码"

接邮件验证码时踩到一个很隐蔽的坑，值得单独记下来：

**症状**：同一段代码连续跑两轮，结果不一致 —— 一轮"60 秒冷却生效"，另一轮没生效；
用户收到两封验证码邮件，用第一封的码注册却报"验证码不正确"。

**根因**：验证码存在固定 KV 键里，后一次发码覆盖前一次；而 Cloudflare KV 是**最终一致**的，
写完立刻读可能读到旧值。于是「是否覆盖」取决于读没读到旧值 —— 读不到就生成新码覆盖旧码，
用户手上的旧码当场作废。

**解法：把验证码本身放进 KV 键名**（`vcode:<用途>:<邮箱>:<验证码>`）。

| 好处 | 说明 |
|---|---|
| 多枚码天然并存 | 用户手上**任何一封**邮件里的码都还有效，不会出现"第二封把第一封作废" |
| 校验 = 精确查找 | 按输入的码直接 `get`，不依赖任何读-改-写，从根上避开最终一致性问题 |
| 副作用可控 | 冷却/窗口计数偶尔失效时，后果只是"多发一封邮件"，而不是"用户的码被作废" |

**猜码防护是双轨的**，两轨各管各的：

| 层 | 手段 | 作用 |
|---|---|---|
| 安全边界 | **每次猜错都写一次 KV**（分桶键） | KV 免费版每天 1000 次写 → 全站每天最多猜 1000 次 → 6 位码命中率仅 **0.1%/天** |
| 用户提示 | Cache API 精确计数（机房内） | 「还可尝试 N 次」「次数过多，请重新获取」这类准确提示 |

如果只靠缓存计数，攻击者换机房就能无限猜；只靠 KV 计数，又会被最终一致搞出计数回退。两者都要。

## 二、安全性审计结果

### ✅ 本次已修复并上线

| # | 问题 | 严重度 | 处理方式 |
|---|---|---|---|
| 1 | `/check-url` **完全未鉴权**，任何人可让 Worker 代访任意地址 → 开放代理 + SSRF，可用于探测内网 | **高** | 改为必须登录；加"禁止内网 / 本机 / 云元数据地址"校验；加 20 次/分钟限流 |
| 2 | 登录**没有任何限流** → 可离线爆破密码 | **高** | 单账号 15 分钟 8 次失败、单 IP 15 分钟 40 次失败，超出返回 429 |
| 3 | 注册**没有任何限流** → 可批量刷号、烧 KV 写配额 | 中 | 同一 IP 每小时最多注册 5 个 |
| 4 | 登录响应耗时可区分"账号是否存在"（不存在秒回，存在要跑 10 万次 PBKDF2） | 中 | 账号不存在时**也跑一次同样的 PBKDF2**，把耗时对齐 |
| 5 | 发帖只有 30 秒间隔，**没有每日上限** | 中 | 新增每账号每天 30 条上限 |
| 6 | `/publish`、产品改链接时的 HEAD 检测可指向内网 | 中 | 统一走 `assertPublicUrl()` 拦截内网 / 本机 / `169.254.169.254` |
| 7 | `GITHUB_PAT` 已失效（Worker 运行时拉不到目录 → 个人主页产品数为 0） | 中 | 目录读取改为 **KV 优先**，不再依赖运行时 GitHub 调用 |
| 8 | 限流计数占用 KV 写额度，可被恶意刷爆 | 中 | 全部改用 Cache API 计数（见上） |
| 9 | `/users/<任意不存在的名字>` 都能打开一个空白"幽灵主页"（无限 URL 空间，SEO 与爬虫都不友好） | 低 | 账号必须真实存在才返回主页，否则 404；GitHub 账号在 OAuth 登录时自动写入最小资料记录 |

### ✅ 现状本来就良好（无需改动）

- **密码存储**：PBKDF2-SHA256、10 万次迭代、每账号 16 字节随机盐、只存哈希，明文永不落库
- **会话**：`HttpOnly` + `Secure` Cookie、30 天 TTL、KV 只存 session→邮箱映射；账号被封禁立即掉线；退出即删记录
- **密钥管理**：`GITHUB_CLIENT_SECRET` / `GITHUB_PAT` / `ADMIN_KEY` 全部是 wrangler secret，不进仓库
- **管理后台**：白名单邮箱 **+** 管理口令双重校验；口令用常数时间比较（防时序侧信道）
- **XSS**：全站无 `dangerouslySetInnerHTML` / `innerHTML`；用户内容一律走 React 转义；头像**只允许 png/jpeg/webp/gif 的 base64**（**刻意不允许 SVG**，否则可注入脚本）
- **CORS**：固定三个来源白名单，不反射任意 Origin
- **邮箱泄露面**：搜索结果、关注/粉丝列表、帖子、评论**都不返回邮箱**；邮箱只在本人主页、且需本人主动开启
- **限流绕过**：限流按账号 + IP 双维度，不只看账号

### ⚠️ 仍然存在的缺口（建议按此排期）

| 优先级 | 缺口 | 风险 | 建议做法 |
|---|---|---|---|
| ~~P0~~ | ~~邮箱未验证~~ | ~~任何人可冒用你的邮箱注册~~ | ✅ **已修复**：接阿里云 DirectMail 邮件验证码（改邮箱、找回密码强制验；注册时**可选**，填了必验对；未验证不能公开邮箱） |
| ~~P0~~ | ~~没有自助找回密码~~ | ~~用户只能人工重置~~ | ✅ **已修复**：邮件验证码自助重置，且对"账号是否存在"返回完全相同的响应 |
| **P0** | **改密码后旧会话仍有效** | 密码泄露后无法一键踢掉所有设备 | 改密码时清除该账号全部 `session:*`（`pwdVersion` 机制已就位，只差强制清会话） |
| **P1** | **没有 CSP / 安全响应头** | GitHub Pages 不能设响应头，但可用 `<meta http-equiv>` | 至少加 `object-src 'none'; base-uri 'self'; frame-ancestors 'none'`；字体自托管后可加 `font-src 'self'` |
| **P1** | **KV 数据无异地备份** | 一条误删的 `kv key delete` 就永久丢失 | 定时任务把用户/帖子/评论导出 JSON 存到 R2 或另一个仓库 |
| **P2** | **管理员只有邮箱 + 口令** | 口令泄露即失守 | 再叠一层 Cloudflare Access（Zero Trust）保护 `/guanli/` 与管理接口 |
| **P2** | **头像存在 KV 里** | 每个头像最高 300KB，1 GB 存储撑不了多少 | 后续迁到 R2，KV 只留引用 URL |
| **P2** | **帖子不可编辑** | 用户发错只能删了重发 | 允许作者在 10 分钟内编辑 |
| **P3** | **评论无自助删除** | 已在隐私页如实披露 | 提供"删除我的评论"入口 |

## 二·五、邮件通道（阿里云 DirectMail）

### 为什么是阿里云，而不是 Cloudflare Email Routing / Resend

| 方案 | 能否发任意收件人 | 免费额度 | 结论 |
|---|---|---|---|
| Cloudflare Email Routing | ❌ **只能转发给自己账号内已验证的地址**（免费版 `send_email` 上限 200 个 destination） | — | **不可用于验证码**，它只是入站转发 |
| Cloudflare Email Sending | ✅（2026-04 公测） | **强制 Workers Paid $5/月**（含 3000 封/月，超出 $0.35/千） | 能用，但为了发验证码先掏 $5/月不值 |
| Resend | ✅ | 3000 封/月，但**每天上限 100 封** | 日常够，突发不够；且国内送达与合规不如阿里云 |
| **阿里云 DirectMail** | ✅ | **共 2000 封免费额度，每天最多免费 200 封**，超出 ¥2/千 | ✅ **选定方案** |

### 费用风险怎么做到零

阿里云「免费发信量」的规则是：**每个主账户共 2000 封免费额度，每天最多免费发送 200 封**；
**超过免费额度的部分会自动转按量计费**（¥2/1000 封）。

这条规则可以用接口直接读出来（`DescAccountSummary`），**不要靠控制台截图猜**：

| 字段 | 含义 | 本项目实测值（开通时） |
|---|---|---|
| `RemainFreeQuota` | **总**免费额度剩余 | 2000 |
| `DailyRemainFreeQuota` | **日**免费额度剩余 | 200 |
| `DailyQuota` | 日发送上限（由信誉等级决定，**不是免费额度**） | 2000 |
| `MonthQuota` | 月发送上限 | 62000 |
| `QuotaLevel` / `MaxQuotaLevel` | 当前信誉等级 / 用户设定的最高等级 | 2 / 2 |
| `IpChannelType` | 出口通道，normal = 正常通道 | normal |

> ⚠️ **`DailyQuota=2000` 是个陷阱**：它是信誉等级决定的**发送上限**，超了发不出去；
> 而**免费**额度只有 200 封/天。从第 201 封起就已经按 ¥2/千 计费了。
> 真正的"免费/收费"分界线是 `DailyRemainFreeQuota`。

所以真正要防的不是"用超额度"，而是"被刷到超额"。三层防线：

| 层 | 手段 | 效果 |
|---|---|---|
| **主防线** | Worker 侧每日 **150 封** / 累计 **1800 封** 配额（KV 权威计数，全球收敛） | 超了直接返回"额度已用尽"，**根本不会去调阿里云** → 费用恒为 ¥0 |
| 地板 | 阿里云**概览页 → 最高信誉等级限制** 设为 1 级 | 账号级日额度 500 封/天（最低档）。这是阿里云侧唯一的闸门，**控制台没有「每日发送量上限」这个选项** |
| 熔断 | 阿里云返回配额类错误 → Worker 写 `vcode:fuse` 标记 → 1 小时内不再调用阿里云 | 避免反复去撞阿里云、也避免刷屏式报错 |

> 💡 信誉等级与日额度对照（官方）：1 级 500 / 2 级 2,000 / 3 级 5,000 / 4 级 8,000 /
> 5 级 10,000 / 6 级 20,000 / 7 级 50,000 / 8 级 100,000 … 16 级 1,000 万。
> **最低初始等级就是 2 级**（对应 2000 封/天），所以默认状态其实已经是"最低档附近"。
> 自动升级要求日发 300+ 且送达率 >92%、无效地址率 <5%、垃圾邮件率 <2.5%，
> 升级也不会超过用户自己设的等级上限 —— **把上限压到 1 级就锁死了**。
>
> ⚠️ **别再找「日发送量上限」了 —— 阿里云官方明确说过「邮件推送无法设置每日发送上限额度」，控制台里没有这个选项。**
> 账号级能设的只有**最高信誉等级限制**（概览页），1 级 = 500 封/天。
>
> ⚠️ **配额计数必须放 KV，不能放 Cache API。** Workers Cache API 是 *data center local*
> （官方文档明说数据不跨机房同步，本项目实测 `request.cf.colo` 在 LHR/AMS 间跳变）——
> 拿它当限额用等于形同虚设：攻击者把请求分散到多个机房，日额度能被放大几十倍。
> Cache API 只适合放"同 IP 每小时 10 次"这类粗粒度辅助计数。
>
> 兜底还有阿里云**费用中心的预算告警**，以及 ¥2/千 的实际单价 —— 即使防线全破，
> 1000 封验证码也才 ¥2，一封 ¥0.002，损失上限可接受。

### 签名实现要点（踩过的坑）

阿里云 DirectMail 用 RPC 风格 HMAC-SHA1 签名，**百分号编码必须与官方 SDK 逐字节一致**：

```js
encodeURIComponent(str)
  .replace(/!/g, "%21").replace(/'/g, "%27")
  .replace(/\(/g, "%28").replace(/\)/g, "%29")
  .replace(/\*/g, "%2A");
```

- 官方文档的示例期望值**自相矛盾**（参数清单里 `AccountName=` 为空，示例却用 `<a%b'>`），**以 SDK 实现为准**。
- 少编码 `!` `'` `(` `)` 中任何一个 → 服务端返回 `SignatureDoesNotMatch`。
  这几个字符在邮件正文里非常常见（比如"验证码 10 分钟内有效"如果写成括号形式）—— 不注意就会踩。
- 回归测试固化在 `scripts/test-aliyun-sign.mjs`，与官方 SDK `@alicloud/openapi-core` 交叉比对，**改签名逻辑前必须先跑它**。

### 增长到什么程度会出事（按当前实现估算）

| 日活 | 世界页加载/天 | KV 读/天 | KV 写/天 | 结论 |
|---|---|---|---|---|
| 50 | 1,500 | 27 万 | 500 | **读配额先爆**（10 万/天） |
| 200 | 6,000 | 108 万 | 2,000 | 读写都爆 |
| 1,000 | 30,000 | 540 万 | 15,000 | 必须付费 + 换存储 |

> 估算口径：世界页每次加载约 180 次读、每帖 5 次写。**注意读额度的增长速度是用户的 180 倍**——这是全部问题里最该先解决的。

### 会丢数据 / 会挂吗

- **KV 是最终一致的**（全球缓存，60 秒内传播）。写完立刻在另一个机房读，可能还是旧值。同一区域通常立即可见，所以"发完看不到自己帖子"的概率低，但**多地访问不一致是真实存在的**。
- KV 单键 25 MiB、整体 1 GB：1 万用户 + 1 万帖子 + 评论，也就几十 MB，**存储撑得住很久**；真正的约束是**每日写次数**。
- Workers 免费版 CPU 10 ms：PBKDF2 10 万次迭代实测生产环境正常（注册/登录都跑通了）。如果将来偶发 1102 错误，优先降迭代次数或把密码哈希搬到 D1。
- 静态站在 GitHub Pages：CDN 全球分发，不受 Worker 额度影响，**这部分很稳**，可以放心继续用。
- **最需要优化的点**：世界页 feed 的 180 次并发 KV 读。高并发下不仅吃额度，还会因 KV 60 秒最终一致延迟而变慢。

## 四、升级路线（按用户量分档）

### 阶段 0 · 现在（0–500 用户）—— 把免费额度榨干且不翻车　成本 ¥0

1. **feed 改成"一个键存一页"**：把渲染好的前 30 条帖子存成单个 KV 键，读 1 次而不是 180 次 → **读额度直接降 100 倍以上**。
2. **帖子键合并**：`post:<id>` / `:likes` / `:comments` 合并成一个键 → 每帖从 3 次读降到 1 次读。
3. **世界页加缓存**：热门内容用 Cache API 缓存 30 秒，KV 读再降一个数量级。
4. ✅ 本次已完成：限流体系 + SSRF 防护 + 限流不占 KV 写额度。
5. **加 KV 备份定时任务**（Workers Cron 每天导出到 R2 或仓库）。

**预期：免费额度可撑到日活 500–1000。**

### 阶段 1 · 日活 500–2000 —— 升级 Workers Paid（$5/月）

- 立刻拿到：1,000 万请求/月、KV 1,000 万读/月 + **100 万写/月**、CPU 30 秒上限
- **性价比最高的一档**：基本不用改代码，只换套餐就能扛住 10 倍流量
- 同步要做：换新的 `GITHUB_PAT`（恢复"提交即同步到静态目录"）、数据备份
- 邮件通道此时会明显吃紧：免费额度每天 200 封，日活 500 时每天的验证邮件就可能超。
  届时二选一 —— ① 阿里云按量付费（¥2/千，1000 封才 ¥2，成本极低，不必纠结）；
  ② 把 Worker 侧的 `DM_DAILY_BUDGET` / `DM_TOTAL_BUDGET` 调高，并把阿里云概览页的
  **最高信誉等级限制**一起调高，再留好预算告警。
  （阿里云侧**没有**「每日发送量上限」可设，只能靠信誉等级限制间接控制。）

### 阶段 2 · 日活 2000–10000 —— 帖子/评论迁到 D1

- D1（Cloudflare 自带 SQLite）适合帖子、评论、点赞：能建索引、能分页、能 JOIN、能聚合

- 迁移要点：`posts(id, author, text, link_url, created_at)` + `comments` + `likes`（唯一索引）+ `follows`
- **验证码与配额一并迁到 Durable Objects**：DO 提供强一致读 + 原子计数 + 串行化，
  能一次性解决 KV 最终一致带来的"冷却失效 / 计数回退"，并把 KV 写额度彻底解放出来。
  迁移后每封验证码的 KV 写消耗从 2 次降到 0 次。
- 工作量估计：1–2 天

### 阶段 3 · 日活 1 万+ —— Durable Objects + Queues

- **DO**：关注数/粉丝数等强一致计数、实时热榜（现在榜单是构建期算的，做不了实时排序）
- **Queues**：把"提交后自动播报""官方推荐"这类异步任务从请求里挪出去
- **缓存层**：热门产品 / 热门作者用 KV 或 R2 缓存
- **托管**：静态站可继续留在 GitHub Pages；也可迁到 Cloudflare Pages + Workers Static Assets → 同域、免 CORS、更快

## 六、数据备份与恢复（2026-11-04 起）

### 为什么是自己做的

CloudBase PostgreSQL 的**自动备份 / 手动备份 / 时间点恢复都由底层腾讯云 PostgreSQL 提供，
且只对独享实例开放**。本环境是共享实例（`postgres-b140irpg`，`TenantType: SHARED`，
套餐 `baas_trial` 体验版），控制台里没有备份入口 —— 不是没开，是这个档位没有这项能力。

云存储这条路在同一次排查里也被排除了：PG 环境的旧 COS SDK 直接返回
`STORAGE_NOT_SUPPORTED`（提示升级 SDK），pgstore 又还没进 `@cloudbase/node-sdk@3.18.7`。
所以备份落在**数据库自己的表**里。

### 现在的机制

| 项目 | 值 |
|---|---|
| 表 | `public.kv_backup`（迁移 `20261104020000_create_kv_backup.sql`） |
| 形态 | 一天一份全量键值，`PRIMARY KEY (taken_on, key)` |
| 触发 | `solhub-cron` 的 `backup-daily` timer，每天 **03:30**（北京时间） |
| 保留 | **30 天**，每次备份顺手删掉 30 天前那份 |
| 体积 | 约 57 行 / 28 KB 一份（头像已外置，仍在同一张表里）→ 30 天约 1 MB |
| 权限 | 只有 `service_role` 有 GRANT，`anon` / `authenticated` 零授权且 RLS 开启 |
| 状态记录 | KV 键 `backup:days`（已有哪些日期）、`backup:last`（最近一次的行数与耗时） |

同一天重复跑只**覆盖**当天那份（先按 `taken_on` 删除再批量插入），不会累积重复快照。

### 过期键清理（2026-11-04 起）

KV 兼容层的 `get` 只把「已过期」当作不存在，**行一直留在表里**。原先全库只有备份、
没有任何清理，`session:*`（30 天 TTL）会无限堆积，还被每天的快照复制 30 份。

现在每次 `backup` 之后会顺带跑一次 `purgeExpired()`：

- 只删 `expires_at` 非空、且已经到期的行；用户 / 资料 / 产品目录 / 关注关系的
  `expires_at` 都是 `NULL`，SQL 与 JS 两层都判不到它们。
- **顺序是「先备份再清理」**：被删掉的行在当天快照里仍然存在，30 天内可 restore 找回。
- 清理失败不影响备份结果，错误挂在返回值的 `purge` 字段上。

### 怎么手动备份 / 恢复

都走 `solhub-cron` 这一个函数，用 `action` 分流：

```bash
# 立刻备份一次（备份完自动清理过期键；带 "dryRun": true 则只统计不删）
{ "action": "backup" }

# 只清理过期键，不备份
{ "action": "purge", "dryRun": true }

# 预览某天的恢复（不写库）
{ "action": "restore", "confirm": "RESTORE", "dryRun": true }

# 真恢复（默认取 backup:days 里最新的一天；也可传 "takenOn": "2026-11-04"）
{ "action": "restore", "confirm": "RESTORE" }
```

控制台「云函数 → solhub-cron → 测试」里粘贴上述 JSON 即可，或用 MCP 的 `invokeFunction`。

**恢复的语义是「补回」而不是「整库回滚」**：快照里有的键覆盖写回，快照里没有、
库里现在有的键**保留**。这样误删/改坏能救回来，又不会把备份之后新注册的用户一起抹掉。
真要整库回到某一天，先手动 `DELETE FROM kv` 再恢复 —— 属于人工决策，没放进自动化。

### 它兜得住什么、兜不住什么

| 场景 | 结果 |
|---|---|
| 误 `DELETE` / 误 `UPDATE` 一批键 | ✅ 恢复到当天快照 |
| 迁移脚本或代码缺陷写坏数据 | ✅ 同上 |
| 实例被销毁 / 环境被回收 / 账号异常 | ❌ **表和数据同生共死** |

要覆盖最后一类，只有两条路：① 升级到独享实例用平台备份（顺带拿到 PITR）；
② 定期把快照导一份到环境之外。导出可以直接用只读 SQL：

```sql
COPY (SELECT taken_on, key, value, expires_at FROM public.kv_backup
      WHERE taken_on = '2026-11-04')
  TO STDOUT WITH (FORMAT csv, HEADER true);
```

> ⚠️ 导出文件里含密码哈希（`pw:*`）、会话令牌（`session:*`）、验证码（`vcode:*`），
> 落到本地后要按密钥对待：不要进仓库、不要发聊天工具、用完删掉。

### 每月该做的一次演练

备份只有在能恢复时才成立。每月挑一天，跑一次 `restore` + `dryRun: true` 看行数对不对，
再抽查 2~3 个键（比如自己的 `user:` 记录）确认内容完整。行数明显少于线上 `SELECT count(*) FROM kv`
就说明备份链路出问题了。
